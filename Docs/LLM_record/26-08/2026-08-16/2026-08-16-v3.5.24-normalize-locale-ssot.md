## 一、问题分析

### 核心症状与根本原因

| 遗留项 | 现状 | 根因 |
|---|---|---|
| ① 非支持语言值折叠 zh-CN | 远端/本地偏好中出现 `'fr'` 等非支持值 → `normalizeLocaleLanguage('fr')` 的 else 分支写死返回 `'zh-CN'` | `normalizeLocaleLanguage` 契约「非 en-us 一律 zh-CN」把「不支持的语言」误判为「中文」；V3.5.23 只在偏好映射层补了**空值**兜底，非空非支持值仍走原 else 分支 |
| ② README 尾注过期 | 演进表已收敛为 V3.5.23/22/21 三行，但「更早版本（V3.3.21 及以前）」注释暗示表内仍含 V3.5.20 及更近版本 | 收敛时未同步更新注释的截止版本 |

### 调用点核验（决定 SSOT 级修改安全）

`normalizeLocaleLanguage` 全仓库仅 3 个调用点：
- `useLocale.js` `readInitialLanguage`（存储值非空 → 归一；脏数据 `'fr'` 目前会折叠 zh-CN）
- `useLocale.js` `setLocaleLanguage`（显式输入路径，实际调用方只传 zh-CN/en-US）
- `useUserPreferencesStore.ts` `normalizeLanguage` 包装（`normalizePreferences` / `savePreferences` / `readCachedPreferredLanguage`）

全部可安全接收新契约：**非 zh-CN/en-US（含空、缺失、脏数据）→ `detectSystemLanguage()`**，与 V3.5.22 起的「否则默认英文/跟随浏览器」策略一致，且一改全链路（含 localStorage 脏 key 路径），无需在各归一函数重复兜底。

### 选定方案

1. `useLocale.js`：`normalizeLocaleLanguage` else 分支由 `'zh-CN'` 改为 `detectSystemLanguage()`，更新 jsdoc。
2. `useUserPreferencesStore.ts`：V3.5.23 新增的 `normalizePreferenceLanguage`（空值兜底）在新契约下冗余 → 删除，`normalizePreferences` 还原为直接 `normalizeLanguage(raw?.language)`；`detectSystemLanguage` import 保留（DEFAULT_PREFERENCES / applyRuntimePreferences 仍用）。
3. 两组件本地归一同步收口：`FloatingAccountPanel.vue` 本地 `normalizePreferences` 与 `PreferencesTab.vue` 本地 `normalizeLanguage` 均改为「显式仅认 zh-CN/en-US，其余 → `detectSystemLanguage()`」。
4. `README.md`：尾注「更早版本（V3.3.21 及以前）」改为「（V3.5.20 及以前）」对齐表尾。

## 三、修改原因

用户要求彻底消除「非中文语言被误判为中文」的缝隙；SSOT 级修改使 localStorage 脏 key、远端脏数据、表单本地归一三链路行为统一（中文 → zh-CN，其它 → 浏览器默认）。README 尾注修正保持文档与表实际内容一致。
